# ADR-0003: Локальное сохранение в .properties с резервной копией

* **Статус:** Принято
* **Дата:** 2026-10-23
* **Автор:** Ефлаков Д.Д.
* **Связанные требования:** `FR-006`, `FR-007`, `NFR-002`

## Контекст и постановка задачи
Приложение должно локально сохранять прогресс игрока каждые 30 секунд и при выходе из игры, гарантируя защиту от потери данных при внезапном отключении питания или повреждении файла сохранения, при этом не раздувая сроки разработки и внешние зависимости проекта.

## Рассмотренные варианты
1. **Стандартный формат `java.util.Properties` (`~/.starforge-clicker/save.properties`) с атомарной записью через временный файл и резервной копией `save.properties.bak`**
2. **Сериализация в JSON с подключением библиотеки Jackson / Gson**
3. **Встроенная реляционная СУБД SQLite (через JDBC-драйвер)**
4. **Стандартная бинарная `java.io.Serializable`**

## Принятое решение
Выбран вариант **1: хранение в `java.util.Properties` с резервной копией `.bak`**.

### Обоснование
* **Плоская структура данных:** состояние игры состоит из 5 скалярных полей (`dust`, `totalEarned`, `totalClicks`, `playSeconds`, `savedAt`), ключей `upgrade.<NAME>` и CSV-строки `achievements`, что идеально ложится на формат «ключ = значение».
* **Нулевые внешние зависимости и экономия времени:** `java.util.Properties` встроен в JDK, человекочитаем при отладке и не ломается при изменении сигнатур классов (в отличие от бинарной сериализации).
* **Отказоустойчивость (`FR-007`):** `SaveManager` сначала записывает данные во временный файл, переносит предыдущее валидное сохранение в `save.properties.bak` и заменяет основной файл. При ошибке чтения или некорректных значениях (`dust < 0`, `NaN`) автоматически загружается `.bak`.

## Последствия
* **Положительные:** сокращение трудоёмкости подсистемы сохранения на 2 часа (по итогам Раунда 1 с Заказчиком), высокая скорость записи (< 2 КБ на диске).
* **Отрицательные:** при чтении чисел требуется явный парсинг `Double.parseDouble` / `Long.parseLong` с перехватом `NumberFormatException`.
